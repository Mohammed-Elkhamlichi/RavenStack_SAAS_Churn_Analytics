2. Relationships to investigate
Before building the Power BI model, verify these relationships:
Relationship	Expected cardinality
Accounts → Subscriptions	One-to-many
Accounts → Churn events	One-to-many
Subscriptions → Feature usage	One-to-many
Accounts → Support tickets	One-to-many

Do not assume that these relationships are enforced by database constraints. Check for orphan records and duplicate keys.

An important detail: dim_churn_events may contain multiple churn events per account, especially because it has is_reactivation. This could represent repeated churn and reactivation cycles.

That makes it particularly important not to treat dim_accounts.churn_flag as a complete historical churn measure.

5. Critical limitations and assumptions to investigate
I want to highlight six things before you start writing more SQL. These can make or break the credibility of the project.
Issue	Why it matters
Multiple subscriptions per account	Subscription counts cannot be treated as customer counts.
Multiple churn events per account	Reactivations can make event counts different from unique churned customers.
churn_flag versus churn events	These fields may represent current status versus historical events.
MRR and ARR	We need to establish whether these are current values, historical values, or subscription-level values.
Upgrade/downgrade flags	Flags alone don't tell us exactly when revenue changed.
Feature usage	Usage connects to accounts through subscription_id, so joining requires care.

The most important limitation: Your subscription table has start_date, end_date, mrr_amount, and upgrade/downgrade flags, but no explicit upgrade or downgrade event dates.

If each subscription row represents one subscription period, we can analyze subscription-level revenue and lifecycle. But we cannot automatically reconstruct the exact historical MRR movement caused by upgrades and downgrades.

Similarly, trial conversion is potentially measurable, but we must first establish how trial and paid subscriptions are represented.

7. Your next step: Dataset validation
Before continuing with Change Over Time, I recommend running these checks.

Check 1 — Table sizes
SELECT 'dim_accounts' AS table_name, COUNT(*) AS rows
FROM analytics.dim_accounts

UNION ALL

SELECT 'dim_churn_events', COUNT(*)
FROM analytics.dim_churn_events

UNION ALL

SELECT 'fact_subscriptions', COUNT(*)
FROM analytics.fact_subscriptions

UNION ALL

SELECT 'fact_feature_usage', COUNT(*)
FROM analytics.fact_feature_usage

UNION ALL

SELECT 'fact_support_tickets', COUNT(*)
FROM analytics.fact_support_tickets;


This will also help reconcile the README's row-volume information with the five tables in your database.

Check 2 — Account and subscription relationships
SELECT
    COUNT(*) AS total_subscriptions,
    COUNT(DISTINCT account_id) AS unique_accounts,
    COUNT(*) - COUNT(DISTINCT subscription_id)
        AS duplicate_subscription_ids
FROM analytics.fact_subscriptions;


Check 3 — Churn event behavior
SELECT
    is_reactivation,
    COUNT(*) AS total_events,
    COUNT(DISTINCT account_id) AS unique_accounts
FROM analytics.dim_churn_events
GROUP BY is_reactivation;


Check 4 — Subscription lifecycle
SELECT
    churn_flag,
    COUNT(*) AS subscriptions,
    COUNT(*) FILTER (
        WHERE end_date IS NULL
    ) AS without_end_date
FROM analytics.fact_subscriptions
GROUP BY churn_flag;


Check 5 — Revenue consistency
SELECT
    COUNT(*) AS total_subscriptions,
    SUM(mrr_amount) AS total_mrr,
    SUM(arr_amount) AS total_arr,
    AVG(mrr_amount) AS avg_mrr,
    AVG(arr_amount) AS avg_arr
FROM analytics.fact_subscriptions;


This is an initial consistency check, not yet a calculation of current company-wide MRR.
